# Design plan (parallel session): Ticketing Portal, iteration 1

This was written in a parallel session, for the executor to build from. The clickable mockup is at [index.html](index.html), and its tokens are at [m3-tokens.css](m3-tokens.css). The tokens are generated by [generate-tokens.mjs](generate-tokens.mjs).

> **Two plans exist.** The executor started Phase 6 before this landed and wrote its own [`docs/design-plan.md`](../design-plan.md). This file sits beside the mockup instead of overwriting that one. Both plans agree on the seed, SchemeContent, the fonts, the tone, the banned list and the violet-tertiary correction. They differ in one real way:
> - **The KB answer panel's surface:** the executor's plan uses `primary-container`, the dark seed slab in both modes. This one uses `secondary-container`, for the reasons in §7, item 1. The screenshots show how this version looks.
>
> The user decides which one wins. The loser's differences go under "Changes during build".

Precedence: **brief > `material-3` > `frontend-design`**. PLAN.md §0 is locked, and this document works inside it. Where this plan differs from §0, it's flagged under [Flags for §0](#flags-for-0-not-changed-here), not silently changed.

## 1. Subject, audience, job

The product is the support desk for a subscription web app with workspaces, seats, invoices, reports, SSO and a mobile app. The seeded KB articles and the demo tickets are written about this product.

| | End-user portal | Agent console |
|---|---|---|
| **Who** | Customers of the app, like Uma User and Leo Client. They're usually mid-problem: locked out, billed wrongly, or blocked at work. They visit a few times a month. | Support agents: Tara and Tom (tier 1) and Sasha (senior). They keep the console open all day and work through 20 to 60 tickets per shift. |
| **Primary job** | "Get my answer, or get a person on it, and know what happens next." The KB answer comes first. A request is the fallback, and its status is visible without opening it. | "Know which ticket needs me next, and act on it without leaving the queue." SLA urgency is visible at a glance, and triage, reply and status are one pane away. |
| **Emotional register** | Reassurance. Plain words, room to breathe, one thing asked at a time. | Control. Everything countable is counted, every state has a word, and nothing moves unless the agent moves it. |
| **Vernacular** | "Your requests", "Waiting on you", "Reply to reopen". There's no ticket jargon, no status codes and no internal IDs up front. | Ticket IDs (`TCK-01040`), SLA countdowns, "Internal note", "Escalate", triage fields. The job's own vocabulary is kept. |

## 2. Stated choices (the brief requires these up front)

- **Seed color:** `#1E6A5E` "Spruce", expanded with `SchemeContent` at contrast 0, light and dark.
- **Display typeface:** Google Sans Flex. Display and headline roles use the `ROND` axis at **60** on the end-user portal and **0** on the agent console. Verified axes on fonts.google.com: `GRAD 0–100`, `ROND 0–100`, `opsz 6–144`, `slnt −10–0`, `wdth 25–151`, `wght 1–1000`.
- **Body typeface:** Roboto Flex, for title, body and label roles. `opsz` is automatic, so 12–14px agent tables get the small-size optical cut. IDs, times and countdowns use `font-variant-numeric: tabular-nums`. **There is no monospace face.**
- **Tone:** *calm, spacious and reassuring for the end-user portal; dense, scannable and efficient for the agent console.*

| Citation markers `[n]` | `primary` / `on-primary`, `full` corners | Small, high-contrast, and they link to their chips |
| Source chips | `surface-container-lowest` / `on-surface`, with the number in `primary` | Lifts off the answer panel |
| "New request" extended FAB | `primary-container` / `on-primary-container` | This is where the seed shows exactly as chosen. It's dark in both modes by design |
| Requests list | `surface-container-low`, `large` corners, `outline-variant` dividers | A list, not cards |
| "Waiting on you" chip | `--attention-container` / `--on-attention-container` | See 3.3 |
| Other status chips | Outlined: `outline-variant` border, `on-surface-variant` label | Neutral. Color isn't spent on status |

| Dividers | `outline-variant` | `material-3` rule |

### 3.3 One component-level alias

SchemeContent puts `tertiary-container` at T40 in **both** modes, which makes a dark violet slab in light mode. The plan wants a light "tint" for internal notes and for "Waiting on you". So the mockup defines one mode-aware alias, built only from legal M3 pairs:

```css
/* light */ --attention-container: var(--md-sys-color-tertiary-fixed);     --on-attention-container: var(--md-sys-color-on-tertiary-fixed);
/* dark  */ --attention-container: var(--md-sys-color-tertiary-container); --on-attention-container: var(--md-sys-color-on-tertiary-container);
```

`tertiary-fixed` and `on-tertiary-fixed` are the designated pair for a container that keeps its tone across modes. In the MUI theme, this becomes one custom palette entry, `attention`, resolved per mode.

### 3.4 Type roles

| Where | Role |
|---|---|
| End-user page title ("What do you need help with?") | `display-small`, Google Sans Flex, ROND 60 |
| End-user section heads ("Your requests") | `headline-small`, ROND 60 |
| End-user ticket title | `headline-medium`, ROND 60 |
| Answer text | `body-large` |
| List item title / supporting text | `body-large` / `body-medium` |
| Agent ticket title | `title-large` (Roboto Flex). Headlines aren't used in the console |
| Agent queue cells | `body-medium` 14/20. IDs and times use tabular figures |
| Agent column headers, chip labels | `label-medium` / `label-large`, **sentence case, never uppercase** |
| Buttons | `label-large`, `text-transform: none` |

### 3.5 Shape, elevation, motion

- **Shape:** `full` for buttons, chips, the search bar and citation markers. `extra-large` (28) for the answer panel. `large` (16) for the requests list and the end-user thread. `small` (8) for agent panes and the table. `medium` (12) for the AI panel groups. Never a raw `border-radius`.
  - §0 says chips stay pill-shaped in both portals, which overrides the M3 default of `small` for chips. That follows the brief's "fully rounded corners by default".
- **Elevation:** tonal only. `box-shadow` isn't used anywhere, and MUI `shadows` are all `none`.
- **Motion:** `--md-sys-motion-*` tokens. One orchestrated moment: the answer panel resolves from a skeleton (`medium4`, `emphasized-decelerate`) when a search is submitted. There are no entrance animations on load. Hover and press state layers use `short2`. `prefers-reduced-motion` turns off everything except opacity.

## 4. Layout concepts

### 4.1 End-user portal

**Concept:** a quiet help desk. It's one left-aligned column (max 880px) where the question you type is answered in place, and your requests sit underneath as a short list of what's happening.

- Content is **left-aligned** inside the column. The column is centered on large windows, as `material-3` requires for 1200px+ (840–1040px max).
- Nothing is centered as a hero, and there's no illustration.

## 5. Per-portal contrast (from PLAN.md §0, made concrete)

| | End-user portal | Agent console |
|---|---|---|
| Density | 16px body, 24–32px gaps, 72px list rows, max width 880px | 14px body, 36px table rows, 8px gaps, full-bleed |
| Surfaces | `surface` + `surface-container-low`, one tinted panel | Layered: `surface-container` rail → `surface` queue → `surface-container-low` thread → `surface-container-high` side panel → `surface-container-highest` selected row |
| Layout | Top app bar and one column | Nav rail and 3 panes (list-detail + supporting pane) |
| Shape | `extra-large` / `large` containers, pill buttons | Pill buttons and chips, `small` panes and table |
| Type personality | Google Sans Flex ROND 60 headlines | ROND 0. No headlines; `title-large` is the largest |
| Signature element | **Grounded answer panel** | **SLA ring countdown** on every row |

### Signature elements

1. **Grounded answer panel.** The answer text carries inline citation markers `[1]` `[2]`, and each marker links to a numbered source chip with the real article title. The panel says what it's grounded in ("Answer from 2 help articles") and ends with the fallback action ("Submit a request").
   - States:
     - loading: a skeleton with 3 lines and 2 chips
     - answered
     - no answer: "We couldn't find this in our help articles." plus a filled "Submit a request" button
   - The numbering is legitimate because it maps to citations, the one numbered-marker use §0 allows.
2. **SLA ring.** An 18px SVG ring. Its arc shows the fraction of the SLA window left, next to a tabular countdown.
   - States:
     - on track: `primary` arc and the time
     - at risk: `tertiary` arc, the time and the word "At risk"
     - breached: a full `error` ring, the time over and the word "Breached"
     - paused: a dashed `outline` ring and "Paused"
     - none (resolved/closed): no ring and "Stopped"
   - Every state has an `aria-label` sentence ("At risk, 40 minutes left on first response").
   - On track shows no state word on purpose. The countdown is the text, and a word on 60% of the rows would be noise.
   - The ring follows the response clock until the first public agent reply, then the resolution clock, which is what `services/sweeps.ticket_at_risk` evaluates.

### End-user status language

| Status | Chip | Supporting line (the latest thing that happened, in plain words) |
|---|---|---|
| `new`, `triaged` | Received | "We're reviewing this" |
| `open` | Open | The assignee's latest public action, e.g. "Tara cleared the reset limit. Try requesting a new link" |
| `in_progress` | In progress | e.g. "Tom is reissuing your invoice with Dutch VAT" (from the latest public agent reply) |
| `pending` | **Waiting on you** (attention tint) | What the agent asked for. Pending rows sort first |
| `resolved` | Resolved | "Reply within 72h to reopen" |
| `closed` | Closed | "Replying starts a new request" |

## 6. Banned (from PLAN.md §0, plus how the mockup avoids each one)

- Drop shadows for elevation: none are used; elevation is tonal.
- Purple gradients: none. Gradients aren't used at all; the tertiary violet is flat, low-chroma and limited to at-risk marks and the attention tint.
- A centered hero with an illustration: the end-user page is left-aligned and has no illustration.
- A card grid of everything: requests are a list, and the queue is a table.
- Inter or system-ui: Google Sans Flex and Roboto Flex only.
- Default MUI blue: the only accent is the spruce primary.
- ALL-CAPS labels: nothing uses `text-transform: uppercase`. MUI buttons, tabs and overline need `textTransform: 'none'`.
- Tracked-out eyebrow labels above headings: none.
- Meta strings joined with middle dots: meta goes in separate spans or columns.
- `WORD — fragment` labels: none.
- A `→` appended to links or buttons: none. The back arrow is a leading navigation icon button, not decoration.
- Accenting a single word in a headline: none.
- Numbered markers on things that aren't sequences: only the KB citations are numbered.
- Fade-and-slide-up entrances on every section: the only reveal is the answer panel, and it's triggered by the user.

## 7. Review against the brief: what changed after the first pass, and why

The first pass was written from §0 alone. I then checked it against the brief, the generated scheme and frontend-design's list of tells, and revised the following.

1. **The answer panel moved off `primary-container`.**
   - The first pass put the signature panel on `primary-container` to "spend the seed" on it.
   - The generated scheme showed SchemeContent puts `primary-container` at T40 in light mode too, which is a dark spruce slab. At the top of a calm page, that reads as a hero block.
   - Moved it to `secondary-container` (T90 light / T30 dark). The seed still appears exactly once per screen, on the "New request" extended FAB.
2. **Internal notes and "Waiting on you" now use a mode-aware attention alias, not `tertiary-container`.**
   - §0 says "tertiary-container tint", but that role is also T40 in light mode, a dark violet slab.
   - Replaced it with `tertiary-fixed`/`on-tertiary-fixed` (light) and `tertiary-container`/`on-tertiary-container` (dark). Both are legal M3 pairs (§3.3).
3. **The end-user page is no longer centered.**
   - The first wireframe centered the headline and search, like a search engine home page. That's the "centered hero" template with the illustration removed.
   - The column is now left-aligned, the headline is plain (no greeting, no name), and the answer panel sits on the same left edge as the search bar.
4. **Status chips are no longer seven colors.**
   - The first pass gave every status its own container color, a rainbow that made color meaningless.
   - Now the only colored chip on the end-user side is "Waiting on you", the one status that asks something of the reader. On the agent side, color is spent on SLA state only. Status and priority are text, and urgent priority gets an `error` icon.
5. **The queue at 1280px became container-query driven.**
   - The first pass had an 8-column table in a 3-pane layout, which doesn't fit at 1280 (the subject column would be about 90px).
   - Now columns appear at container breakpoints, and closing the detail restores all 8. That's M3's list-detail canonical layout, rather than a hidden horizontal scroll.
6. **Human status lines replaced generic ones.**
   - The first pass used "Waiting on you" or "In progress" as the supporting line, which just repeats the chip.
   - Now the line says what actually happened, from the latest public agent reply ("Tom asked you to confirm the last four digits of your card").
7. **Pending rows sort first on the end-user side.** They're the only rows where the reader has to do something.
8. **The ticket-view button says what it does.** A reply on a resolved ticket reopens it, so the button reads "Send and reopen", and on closed tickets it reads "Send as new request". "Submit" isn't used anywhere.
9. **A 3px start bar was added to the selected queue row.** Selection shown by `surface-container-highest` alone measures 1.23:1 against `surface` in light mode (see [md3-audit.md](md3-audit.md)). The `primary` bar measures 7.16:1.

### Flags for §0 (not changed here)

- **§0 calls the tertiary "dusty-rose".** For this seed, SchemeContent produces a **muted violet** (hue 299, chroma 33).
  - I compared the other variants: `SchemeFidelity` gives a terracotta/clay tertiary (hue 34), which is frontend-design's #1 template tell. `SchemeTonalSpot` gives slate blue, but desaturates the primary.
  - I kept SchemeContent's violet. It's flat and low-chroma, and only used for at-risk marks and the attention tint, never as a gradient. The executor or the user should update the §0 wording, or choose a different variant.
- **SchemeContent containers are T40 in both modes.** `primary-container` and `tertiary-container` are dark in light mode. The role map above avoids using them as large light-mode surfaces. Any MUI component that defaults to `primary.container`, such as a selected chip or a tonal button, should be checked in light mode.
- **Node can't import the color-utilities package directly.** `@material/material-color-utilities` 0.4.0 has extensionless relative ESM imports. Vite resolves them, but plain Node doesn't, so `generate-tokens.mjs` registers a small resolve hook. Frontend code going through Vite needs nothing.
